#  Универсална система за резервации (Universal Booking System)
> **Екипен проект по разработка на софтуер • 11. клас**  
> **Технологичен стек:** React 19, Vite, Tailwind CSS, Lucide Icons  

---

##  1. Проблем и цел на проекта

Различните бизнеси (лекарски кабинети, салони за красота, спортни комплекси, зали за събития) имат на пръв поглед коренно различни изисквания за резервации:
- В **лекарски кабинет**: фиксирани кратки интервали (30 мин), строго единичен преглед (1 лекар : 1 пациент) и обедна почивка.
- В **салон за красота**: 45-минутни слотове, индивидуални специалисти и разнообразни естетични услуги.
- В **спортен хъб и конферентни зали**: дълги интервали (60 мин), целодневен режим без прекъсване и **споделен капацитет** (напр. зала за спининг побира до 12 отделни трениращи в един и същи час, а конферентна зала — до 25 души).

Въпреки тези разлики, математическата и логическа същност е една и съща: **управление на ресурси, времеви интервали и капацитет**.

###  Нашето решение:
Създадохме **напълно конфигуруема система**, в която бизнес логиката не е твърдо закодирана (hardcoded), а се определя динамично от конфигурационен модел (`BUSINESS_PRESETS`). Системата включва предварително подготвени симулирани данни за **3 типа бизнес**, високоскоростен алгоритъм за засичане на конфликти.

##  2. Инструкции за бързо инсталиране и стартиране

```bash

npm install

# 2. Стартиране на локалния сървър за разработка
```

### 3.2. Универсален конфигурационен модел (Data Schema)
Всеки бизнес се описва чрез следната универсална JSON структура:

```javascript
{
  id: "medical",
  name: "Медицински център",
  workingHours: {
    start: "08:30",                  // Начало на работното време
    end: "17:30",                    // Край на работното време
    slotDurationMinutes: 30,         // Продължителност на един слот
    breakTime: { start: "12:30", end: "13:30" } // Обедна почивка (или null)
  },
  allowPartySize: false,             // Единичен преглед (1:1) или споделен капацитет
  categories: ["Кардиология", "Педиатрия", ...],
  serviceOptions: ["Първичен преглед", "Ехография", ...],
  resources: [
    {
      id: "med_1",
      name: "Д-р Калоян Петров",
      title: "Главен кардиолог",
      room: "Кабинет 102",
      capacity: 1                    // Максимален капацитет за даден слот
    }
  ]
}
```

##  4. Алгоритми и оптимизации за бързина

> **Ключовият въпрос от условието:** *„Как ще подходите архитектурата и алгоритмите, за да е системата бърза, ефективна и оптимизирана при много ресурси, слотове и промени?“*

### 4.1. Алгоритъм за засичане на конфликти между интервали: $O(1)$
При работа с време използваме **полуотворени интервали**: $[start, end)$.  
За да се избегнат тежки регулярни изрази и сложни проверки, всички часове от тип `"09:30"` се превръщат в брой минути от началото на деня:
$$\text{минути} = \text{hours} \times 60 + \text{minutes}$$

Два времеви интервала $[A_{start}, A_{end})$ и $[B_{start}, B_{end})$ се пресичат тогава и само тогава, когато:
$$A_{start} < B_{end} \quad \land \quad B_{start} < A_{end}$$

```javascript
export function doIntervalsOverlap(startA, endA, startB, endB) {
  return startA < endB && startB < endA;
}
```
Този математически принцип елиминира множество вложени `if-else` конструкции и гарантира моментална $O(1)$ проверка.

### 4.2. Хеш индекс с JavaScript `Map`: търсене за $O(1)$ вместо $O(N)$
Ако в системата има 5 000 резервации, обхождането им с `reservations.filter(...)` за всеки слот на всеки лекар води до тежко забавяне ($O(N \times S)$).

Затова имплементирахме **индексиране с Хеш таблица (`Map`)**:
```javascript
// Ключ: "${resourceId}_${date}" -> Стойност: [масив от активни резервации за деня]
const key = `${res.resourceId}_${res.date}`;
```
- Индексът се изгражда **еднократно** при промяна на резервациите.
- Когато потребителят преглежда лекар в определен ден, съответните резервации се извличат мигновено за **$O(1)$ време**:
  `reservationIndex.get("med_1_2026-11-18")`.

### 4.3. Оптимизация на рендерирането в React (`useMemo` и `useCallback`)
1. **Мемоизация на слотовете (`useMemo`)**: Интервалите за деня (`daySlots`) се генерират само при смяна на бизнеса или работното време.
2. **Изолирано филтриране**: Търсенето по име на специалист в реално време филтрира само масива с ресурси, **без** да преизчислява заетостта на слотовете.
3. **`useCallback`** за всички мутиращи функции (`addReservation`, `editReservation`, `cancelReservation`), което предотвратява пресъздаване на функциите при рендер.

##  5. Демонстрация на 3-те типа бизнес

| Показател | 1. Медицински център | 2. Салон за красота | 3. Спортни събития и наем на зали |
| :--- | :--- | :--- | :--- |
| **Име** | Медицински център | Студио | Спорт, зали и наем на ресурси |
| **Ресурси** | Лекари / Кабинети | Стилисти, маникюристи, барбъри | Тенис кортове, зали за спининг, конферентна зала |
| **Слот стъпка** | **30 мин.** | **45 мин.** | **60 мин.** |
| **Работно време** | 08:30 - 17:30 | 09:00 - 19:30 | 08:00 - 22:00 |
| **Почивка** | 12:30 - 13:30 (Обедна) | 13:30 - 14:15 (Техническа) | Няма (непрекъснат режим) |
| **Модел на капацитета** | Единичен (1 пациент) | Единичен (1 клиент) | **Споделен капацитет (до 12/25 души)** |

##  6. Разпределение на ролите в екипа

Проектът е реализиран чрез съвместна екипна работа с ясно разпределени отговорности:

1. **Иван Kaрдашлиев**:
   - Дефиниране на универсалния конфигурационен модел (`businessPresets.js`).
   - Алгоритъм за засичане на интервали и конфликти (`conflictDetector.js`, `timeUtils.js`).
   - Проектиране на валидацията за пресичане на почивки и работно време.
   - Разработка на централния custom hook `useBookingSystem.js`.
   - Имплементация на хеш индекса (`Map`) за $O(1)$ достъп.
   - Оптимизация с `useMemo` и персистиране на данните в `localStorage`.

2. **Георги Раленеков**:
   - Изграждане на компонентите за визуализация: `ResourceCard`, `SlotGrid`, `BookingModal`.
   - Стилизиране с Tailwind CSS, адаптивен дизайн за мобилни и десктоп екрани.
   - Изработка на визуални състояния: свободни, частично заети, пълни часове и почивки.
   - Тестване на гранични случаи (презастъпване на часове, превишаване на капацитет, невалидни входове).
   - Подготовка на симулираните данни (`initialReservations.js`).

3. **Съвместно разработено от цялия екип**:
   -   Оформяне на цялостната документация (`README.md`).
